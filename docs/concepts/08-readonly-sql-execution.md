# 08 — Read-only SQL execution

> The model proposes SQL; the server decides whether it runs. One grammar check, one table allowlist, one read-only transaction, one timeout, one row cap — and no exceptions.

**Back to:** [Implementation Walkthrough — Step 6](../history/implementation-walkthrough.md#7-step-6--read-only-sql-and-the-nl-to-sql-agent) · [Concept index](../history/implementation-walkthrough.md#concept-index)

> **Current implementation note:** PostgreSQL still uses `pgsql-ast-parser` and a read-only transaction. MySQL-compatible queries use `node-sql-parser`, a read-only transaction request (TiDB's noop error is tolerated), and rollback. MongoDB uses an allowlisted aggregation pipeline or `countDocuments`. All engines enforce row and timeout limits. See [Questions API](../reference/api/questions.md).

## What it is

This is the safety core of the app:

- **AST validation** parses the generated SQL and proves it is one `SELECT`-class statement.
- **A table allowlist** rejects references outside the session's selected tables.
- **A read-only transaction** (`BEGIN TRANSACTION READ ONLY`) makes writes fail even if validation is bypassed.
- **A statement timeout** stops expensive queries.
- **A row cap** stops unbounded result sets.
- **Result normalization** makes rows JSON-safe and limits what reaches the browser and the LLM.

**Prerequisites:** [06 — Database connections & encryption](06-database-connections-encryption.md) (pools and credentials). [07 — Schema introspection & relationships](07-schema-introspection-relationships.md) (selected tables). [09 — LLM provider abstraction](09-llm-provider-abstraction.md) (where SQL comes from).

## Why this project uses it

- The SQL is generated by an LLM, which is influenced by user questions, schema comments, and prior turns. It is untrusted input by definition.
- A single `DROP TABLE` or `UPDATE` would destroy trust in the product. The target role may be read-only, but the app should not depend on the user configuring it correctly.
- A query like `SELECT * FROM events` on a billion-row table can take down a database connection or the API process. Timeout and row cap are product requirements, not optimizations.
- A database error can leak hostnames, role names, or query fragments. The execution layer is where those errors are tamed.

## When to use this pattern

- Any NL-to-SQL feature, SQL console for non-technical users, or read-only analytics assistant.
- Any app that executes SQL assembled by another system.
- **Do not** use “the prompt says not to write” as a control. Prompts are suggestions; the database and the parser are controls.

## How it works here

### Threat model

| Threat | Control |
|---|---|
| Model emits `DELETE`, `DROP`, or multiple statements | AST guard rejects anything not single-statement `SELECT`-class |
| Model joins an unselected table | Table allowlist from the session scope |
| Model calls a data-modifying function | Read-only transaction + non-superuser role |
| Model writes via `SELECT INTO` / `FOR UPDATE` | Explicit AST rejection |
| Query scans forever | `statement_timeout` |
| Query returns millions of rows | Outer `LIMIT max+1` |
| Result contains binary/large values | Cell truncation and JSON-safe conversion |
| Error leaks credentials | Curated error mapping; never echo the connection string |
| Prompt injection says “ignore rules and drop users” | The model has no execution authority; the guard decides |

### 1. AST validation

Use a PostgreSQL-aware parser. `pgsql-ast-parser` is a good fit because it understands PG syntax and lets you walk table references.

```ts
import { parse } from 'pgsql-ast-parser';

export class SqlValidationError extends Error {
  constructor(message: string, readonly sql: string) {
    super(message);
    this.name = 'SqlValidationError';
  }
}

export function validateSql(sql: string, allowed: TableRef[]): string {
  const cleaned = sql.trim().replace(/;+\s*$/, '');
  if (!cleaned) throw new SqlValidationError('The model returned an empty query.', sql);

  let statements: unknown[];
  try {
    statements = parse(cleaned);
  } catch {
    throw new SqlValidationError('The SQL could not be parsed. Only SELECT statements are allowed.', sql);
  }

  if (statements.length !== 1) {
    throw new SqlValidationError('Only one SQL statement is allowed.', sql);
  }

  const statement = statements[0];
  if (!isSelectLike(statement)) {
    throw new SqlValidationError('Only read-only SELECT statements are allowed.', sql);
  }

  assertNoLockingOrInto(statement, sql);

  const refs = collectTableRefs(statement);
  const allowedKeys = new Set(
    allowed.map(t => `${t.schema}.${t.table}`)
  );

  for (const ref of refs) {
    const key = `${ref.schema ?? 'public'}.${ref.table}`;
    if (!allowedKeys.has(key)) {
      throw new SqlValidationError(
        `Table ${key} is outside this session's selected tables.`,
        sql
      );
    }
  }

  return cleaned;
}
```

Do **not** blanket-lowercase both sides. Quoted identifiers are case-sensitive: `public."Orders"` and `public.orders` are different tables. Compare exactly unless your parser exposes whether an identifier was quoted. If it does, normalize unquoted names with PostgreSQL's folding rules and quoted names not at all; if it does not, reject on uncertainty. A false rejection is safe; a false allow is not.

`isSelectLike` should accept:

- `SELECT ...`
- `WITH cte AS (...) SELECT ...`
- `SELECT ... UNION [ALL] SELECT ...`
- parenthesized select/union forms

It must reject:

- `INSERT`, `UPDATE`, `DELETE`, `MERGE`
- `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `COMMENT`, `GRANT`, `REVOKE`
- `COPY`, `VACUUM`, `ANALYZE`, `CLUSTER`, `REINDEX`
- `SET`, `SHOW`, `RESET`
- `EXPLAIN` (unless you explicitly support it later)
- `SELECT ... INTO new_table`
- `SELECT ... FOR UPDATE` / `FOR SHARE`
- multiple statements separated by `;`

The exact AST property names depend on the parser version. Write `isSelectLike`, `collectTableRefs`, and `assertNoLockingOrInto` as small, heavily unit-tested helpers rather than scattering parser assumptions through the route.

### 2. Table reference collection

The collector must:

- Return `{ schema, table }` for real relations.
- Ignore CTE aliases (`WITH recent AS (...) SELECT * FROM recent` should not require a table named `recent`).
- Include tables inside joins, subqueries, and unions.
- Normalize unqualified names to the default schema (`public`).
- Preserve quoted identifiers exactly; compare case-insensitively only if your schema model does.

Test cases that must pass:

```text
SELECT * FROM orders
WITH x AS (SELECT * FROM orders) SELECT * FROM x
SELECT * FROM orders UNION ALL SELECT * FROM archived_orders
SELECT o.id FROM orders o JOIN customers c ON c.id = o.customer_id
```

Test cases that must fail:

```text
SELECT * FROM orders; DROP TABLE orders
SELECT * FROM secret_schema.salaries
WITH x AS (DELETE FROM orders RETURNING *) SELECT * FROM x
SELECT * INTO backup_orders FROM orders
SELECT * FROM orders FOR UPDATE
```

### 3. Read-only execution

```ts
export class TargetDbTimeoutError extends Error {
  constructor() {
    super('The database query timed out.');
    this.name = 'TargetDbTimeoutError';
  }
}

export async function runReadOnlyQuery(
  pool: Pool,
  sql: string,
  options: { maxRows: number; timeoutMs: number }
) {
  const client = await pool.connect();

  try {
    await client.query('BEGIN TRANSACTION READ ONLY');
    await client.query('SET LOCAL search_path = public');
    await client.query("SELECT set_config('statement_timeout', $1, true)", [
      String(Math.max(1, options.timeoutMs))
    ]);
    await client.query(
      "SELECT set_config('idle_in_transaction_session_timeout', $1, true)",
      [String(Math.max(1, options.timeoutMs))]
    );

    const started = Date.now();
    const result = await client.query({
      text: `SELECT * FROM (${sql}) AS _session_query LIMIT ${options.maxRows + 1}`,
      rowMode: 'array'
    });
    const executionMs = Date.now() - started;

    await client.query('ROLLBACK');

    const truncated = result.rows.length > options.maxRows;
    const rows = result.rows
      .slice(0, options.maxRows)
      .map(row => row.map(toJsonSafe));

    return {
      columns: result.fields.map(field => ({
        name: field.name,
        dataType: String(field.dataTypeID)
      })),
      rows,
      rowCount: rows.length,
      truncated,
      executionMs
    };
  } catch (error: any) {
    await client.query('ROLLBACK').catch(() => undefined);
    if (error?.code === '57014' || error?.code === '25P03') {
      throw new TargetDbTimeoutError();
    }
    throw error;
  } finally {
    client.release();
  }
}
```

Why each line exists:

- **`BEGIN TRANSACTION READ ONLY`** — writes fail at the database level.
- **`SET LOCAL search_path = public`** — pins unqualified-name resolution so the allowlist and PostgreSQL agree. Without this, a target role whose `search_path` starts with another schema could resolve `orders` somewhere the allowlist did not check.
- **`set_config('statement_timeout', ..., true)`** — `SET LOCAL` does not accept bind parameters; `set_config` does. The third argument `true` makes it transaction-local.
- **`idle_in_transaction_session_timeout`** — a client that opens a transaction and stalls should not hold locks or a connection forever.
- **Outer `LIMIT max+1`** — caps any query shape, including one that already has a `LIMIT` or `ORDER BY`. Fetch one extra row only to detect truncation.
- **`rowMode: 'array'`** — rows are arrays, so duplicate column names do not overwrite each other.
- **`ROLLBACK`** — read-only work has nothing to commit; always end the transaction.
- **`client.release()` in `finally`** — a leaked client exhausts the pool and makes every later question hang.

### 4. The outer-wrapper caveat

`SELECT * FROM (<sql>) AS _session_query LIMIT n` works for ordinary selects, CTEs, unions, and ordered results. It does **not** work for every statement shape. Because the guard already requires a `SELECT`-class statement without `INTO`/locking, the wrapper is safe for this product. Test it with the exact SQL forms the planner is allowed to produce. If you later allow `EXPLAIN` or `VALUES`, handle those shapes explicitly.

Do not append `LIMIT` by string surgery to the model's SQL. The model may already have a limit, comments, or a trailing semicolon. Wrap the validated result.

Pin `search_path` inside the transaction (or reject unqualified table references entirely). The allowlist compares `schema.table`; if PostgreSQL resolves an unqualified name through a different `search_path`, the two checks can disagree.

### 5. Result normalization

```ts
function toJsonSafe(value: unknown): unknown {
  if (value === null || value === undefined) return null;
  if (value instanceof Date) return value.toISOString();
  if (Buffer.isBuffer(value)) return { type: 'binary', base64: value.toString('base64') };
  if (typeof value === 'bigint') return value.toString();
  if (typeof value === 'object') {
    const text = JSON.stringify(value);
    return text.length > 2_000 ? text.slice(0, 2_000) + '…' : JSON.parse(text);
  }
  return value;
}
```

`pg` already returns `int8` and `numeric` as strings, which preserves precision. Do not cast them to `Number` for display; you will lose digits on large ids and money values.

Also cap individual cell text before sending rows to the LLM:

```ts
function capCell(value: unknown, max = 500): string {
  const text = typeof value === 'string' ? value : JSON.stringify(value);
  return text.length > max ? text.slice(0, max) + '…' : text;
}
```

The UI may show a little more than the LLM prompt, but both should have a hard ceiling. A single `text` column can otherwise blow the context window.

### 6. Error handling and repair

Execution errors fall into two classes:

- **User/model-correctable:** unknown column, ambiguous column, syntax accepted by the parser but rejected by PostgreSQL, wrong aggregate usage. Send a sanitized message back to the planner for **one** repair attempt.
- **Operational:** timeout, connection lost, permission denied. Do not retry the same query blindly. Return `504` or a clear connection message.

```ts
try {
  return await runReadOnlyQuery(pool, sql, limits);
} catch (error) {
  if (error instanceof TargetDbTimeoutError) throw error;
  const repaired = await repairSql(error, question, schema, sql);
  if (!repaired) throw error;
  return await runReadOnlyQuery(pool, repaired, limits);
}
```

Never include the connection string, password, or full server error in a client response. For the repair prompt, pass only the database error code/message needed to fix the SQL. The user can see a curated message and the rejected SQL.

### 7. Read-only role is still required

The transaction and guard are strong, but the role is the last layer:

- A superuser can do things a normal role cannot; the connection test warns about this.
- A role with write grants can still be dangerous if a future code path forgets the transaction.
- The demo target uses `demo_reader` with only `SELECT`. Keep it that way.

Use `default_transaction_read_only=on` in the pool options too. Then even a future non-validated query starts read-only.

## Pitfalls we hit (and fixes)

1. **Multiple statements in one string.** `pg` will happily execute `SELECT 1; DROP TABLE x` through a simple query. The parser must enforce one statement, and the guard must reject the second. Do not rely on a `;` string check; semicolons can appear in string literals.
2. **`WITH ... DELETE`.** A CTE can contain a data-modifying statement. Reject non-select CTE bodies, not just the outer statement.
3. **`SELECT INTO`.** It looks like a select but creates a table. Reject the `into` clause.
4. **`FOR UPDATE`.** It takes locks and is not read-only in spirit. Reject it.
5. **Parser gaps.** A valid PostgreSQL statement may fail to parse. Fail closed: show a validation error and let the planner repair. Never fall back to executing unparsed SQL.
6. **Outer wrapper with trailing semicolons.** Strip trailing `;` before wrapping; otherwise the subquery syntax breaks.
7. **`SET LOCAL` with parameters.** `SET LOCAL statement_timeout = $1` is not valid parameterized SQL. Use `set_config(..., true)`.
8. **Unbounded `text`/`bytea` columns.** Cap cells before sending to the model and rendering in the browser. A single row can exceed the context window.
9. **Leaked clients.** Every `connect()` needs a `release()` in `finally`. A timeout that throws before release is a common pool leak.
10. **Trusting the read-only transaction alone.** It blocks writes to permanent tables, but it does not make unbounded queries cheap. Keep timeout and row cap.
